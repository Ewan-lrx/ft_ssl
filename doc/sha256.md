# SHA-256

## Context

SHA-256 (Secure Hash Algorithm 256-bit) was designed by the U.S. National Security Agency
(NSA) and published in 2001 by NIST as part of the SHA-2 family of hash functions
([FIPS PUB 180-2](https://csrc.nist.gov/pubs/fips/180-2/final), later superseded by
FIPS 180-4). It was introduced to succeed SHA-1, whose theoretical weaknesses were already
becoming a concern at the time, and produces a 256-bit (32-byte) digest.

Unlike MD5, SHA-256 has held up well against cryptanalysis: no practical collision or
preimage attack is currently known against it. It is the hash function underpinning much
of today's security infrastructure — TLS certificates, code signing, password hashing
(combined with a proper KDF), and Bitcoin's proof-of-work, among many others. It remains
the de facto standard choice whenever a general-purpose cryptographic hash is needed.

## How it works

SHA-256, like MD5, is a Merkle–Damgård construction: the message is padded, split into
fixed-size blocks, and processed block by block through a compression function that
updates a running state. The overall shape is the same as MD5's, but nearly every internal
detail differs.

### 1. Padding

The padding scheme is structurally identical to MD5's — pad to a multiple of 512 bits
(64 bytes), append a `1` bit followed by zeros, reserve the last 8 bytes of the final block
for the original message length in bits. The only difference is **endianness**: SHA-256
encodes this length field in **big-endian**, whereas MD5 uses little-endian.

### 2. State initialization

SHA-256 keeps a running state of **eight** 32-bit registers (`h[0]` to `h[7]`, often
labeled `a` through `h`), initialized to fixed values derived from the fractional parts of
the square roots of the first eight prime numbers (2, 3, 5, 7, 11, 13, 17, 19):

```
h[0] = 0x6a09e667   h[1] = 0xbb67ae85   h[2] = 0x3c6ef372   h[3] = 0xa54ff53a
h[4] = 0x510e527f   h[5] = 0x9b05688c   h[6] = 0x1f83d9ab   h[7] = 0x5be0cd19
```

### 3. Message schedule

Before the compression rounds begin, each 64-byte block is expanded into **64** 32-bit
words `w[0..63]` — not just the 16 directly extracted from the block, unlike MD5. The
first 16 words (`w[0..15]`) are extracted directly from the block, in **big-endian**. The
remaining 48 (`w[16..63]`) are derived from previous words through a mixing formula
involving rotations, shifts, and XORs:

```
s0 = rotr(w[i-15], 7) ^ rotr(w[i-15], 18) ^ (w[i-15] >> 3)
s1 = rotr(w[i-2], 17) ^ rotr(w[i-2], 19) ^ (w[i-2] >> 10)
w[i] = w[i-16] + s0 + w[i-7] + s1
```

The purpose of this stage is to spread each block's information across more values than
MD5 does, before mixing even begins — this is one of the structural improvements SHA-256
has over MD5.

### 4. Compression (64 rounds)

Unlike MD5, which uses 4 different mixing functions depending on the round range,
SHA-256 applies the **same** formula across all 64 rounds, each consuming one word
`w[i]`:

```
S1    = rotr(e, 6) ^ rotr(e, 11) ^ rotr(e, 25)
ch    = (e & f) ^ (~e & g)
temp1 = h + S1 + ch + K[i] + w[i]
S0    = rotr(a, 2) ^ rotr(a, 13) ^ rotr(a, 22)
maj   = (a & b) ^ (a & c) ^ (b & c)
temp2 = S0 + maj
```

The eight registers are then shifted (`h=g, g=f, f=e, e=d+temp1, d=c, c=b, b=a,
a=temp1+temp2`), similar in spirit to MD5's register rotation but across 8 values instead
of 4. `ch` ("choose") and `maj` ("majority") replace MD5's four F/G/H/I functions with two
functions reused at every round.

### 5. Finalization

After all blocks are processed, the digest is the concatenation of `h[0]` through `h[7]`,
in **big-endian** — 32 bytes, usually displayed as 64 hexadecimal characters.

## Implementation notes and pitfalls

- **Streaming design (`init` / `update` / `final`)**: as with MD5, data is processed in a
  running 64-byte buffer rather than loaded entirely into memory upfront, which keeps
  memory usage constant regardless of input size.

- **Endianness is the opposite of MD5's**: every byte-ordering operation — extracting
  `w[0..15]` from the block, encoding the length field, writing the final digest — is
  **big-endian**. Reusing MD5's little-endian logic without inverting it is the single
  most common mistake when implementing both algorithms side by side, and it compiles and
  runs without any error, just producing a wrong digest.

- **The message schedule is a distinct, extra step**: it's easy to forget that `w[]` needs
  64 entries, not 16, before the compression rounds can even begin. The 48 derived words
  must be computed in order, since later ones depend on earlier ones in the same array.

- **`ch` needs the negation**: `ch = (e & f) ^ (~e & g)` is easy to mistype as
  `(e & f) ^ (e & g)`, dropping the `~`. This compiles fine and produces a plausible but
  incorrect digest — exactly the kind of silent bug that only shows up against test
  vectors.

- **Eight registers instead of four**: storing them in an array (`h[8]`) rather than eight
  separate named variables makes the final addition step and digest extraction much less
  error-prone, since both naturally become loops instead of eight near-identical lines.

- **The `K[]` table is different from MD5's**: SHA-256 uses its own set of 64 round
  constants (derived from the fractional parts of the cube roots of the first 64 primes),
  distinct from MD5's. Mixing the two up — or reusing MD5's table by mistake if both
  algorithms are implemented in the same codebase — silently produces an incorrect digest.

- **Validating correctness**: test against official vectors, e.g.
  `sha256("") = e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` and
  `sha256("abc") = ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`.
